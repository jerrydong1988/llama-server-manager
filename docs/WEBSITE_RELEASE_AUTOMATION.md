# 官网发版自动化实施方案

## 目标与边界

主程序的正式发布通过既有 release-r2 审批，全部构建及下载源发布成功后，自动将版本资料送往官网仓库。官网继续通过 PR、检查和合并发布，不直接写默认分支。官网失败不撤销已经发布的应用；可以按版本重试。

## 数据与执行顺序

1. 发版 PR 中维护 `docs/release-notes/vX.Y.Z.md`：一级标题为版本与标题，首段为摘要，二级标题下使用无嵌套的条目，末尾保留上一版本到当前版本的比较链接。检查在正式发版前发现缺失或格式错误。
2. 主程序发布完成后，从 GitHub 的正式 Release 读取精确版本及资产，逐一下载并比对 GitHub 与公开 R2 下载的大小和 SHA-256，校验公开更新清单版本。生成 `website-release.json`，作为 Release 资产保留审计记录。
3. 显式通知官网仓库的同步工作流。只传版本标识，接收端重新从可信 GitHub 仓库读取资料、校验格式、资产与版本顺序。普通 release.published 事件不作为发布完成信号。
4. 官网仅更新 `data/release.json`，自动创建或复用 `codex/release-vX.Y.Z` PR。渲染、类型、安全和发布资料检查通过后按仓库规则合并。
5. 官网默认分支检查成功后，串行部署至现有 Cloudflare Worker。部署前确认运行针对当前 main，复查公开下载并记录前一 Worker 版本。部署后检查版本、页面、安全响应头、资源、下载入口及更新清单。
6. 官网自身回归时，只有当前部署仍属于本次任务且上一版健康时才回退；外部下载源故障只报错。保留手动按版本补同步、重新部署和回退入口。

## 权限

跨仓库联动使用只安装在官网仓库的 GitHub App，各任务申请所需的短期权限；主程序发布资料为公开资源，App 无需主程序仓库写权限。官网部署使用专用 Cloudflare API Token，限定账号和所需 Worker/域名权限。密钥只进入 GitHub Secrets，不写入源码或日志。保留 release-r2 原有审批。具体凭据名称和启用步骤见官网仓库 `docs/RELEASE_AUTOMATION.md`。

## 验证与验收

- 单元测试：非法/预发布版本、资料缺失、错误哈希、错误下载地址、旧事件、同版本重复运行、失败恢复。
- 生产渲染测试：首页、下载页和更新说明使用同一资料，五个平台安装包信息一致。
- 两个仓库各自完成相关检查和 PR CI，主程序执行完整 check:release。
- 用当前正式版本 v2.9.47 演练补同步及自动部署，不创建新应用版本。
- 公网验证页面、静态资源、下载跳转、安装包及更新清单；记录工作流和 Worker 版本。

## 运维约束

同一版本的正式资产不可静默更换。新版本缺少完整资料时停止并报错，不从旧版复制说明。生产部署串行，旧提交和旧版本任务退出而不覆盖新内容。长篇使用文档和截图仍需在相应功能 PR 中维护，发版自动化不推测产品行为。
