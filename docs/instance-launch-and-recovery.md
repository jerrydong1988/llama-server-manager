# 实例启动与恢复的维护边界

桌面界面、CLI 和 MCP 对同一配置采用相同的引擎选择和基础命令规则。比较结果时使用同一引擎二进制、能力快照和操作策略，并按顺序比较参数数组。进程创建、服务就绪、后台交接是三个独立的结果。

| 修改意图 | 负责位置 | 回归入口 |
|---|---|---|
| 调整显式引擎、默认引擎或按类型回退的顺序 | [Rust 引擎选择](../src-tauri/src/engine_selection.rs)。桌面成功绑定旧配置后仍先保存、再启动。 | Rust 选择测试；管理接口和浏览器的旧配置用例 |
| 增加或修改启动参数 | [命令构造](../src-tauri/src/commands/server.rs) 和[共享启动计划](../src-tauri/src/commands/server/launch_plan.rs)。预览和启动共用有效配置及基础参数。 | Rust 启动计划测试；[测试引擎实际接收的参数](../scripts/test-management.cjs) |
| 处理完整预览需要重新探测的情形（#177） | Rust 返回结构化诊断；[桌面实例操作](../src/store/instanceSlice.ts) 在明确请求完整预览时按选中引擎探测并重试。普通预览可给出不支持的参数，实际启动会拒绝它们。 | [命令预览的普通、过期、部分探测和失败场景](../browser-tests/command-preview.spec.ts) |
| 跟进 Gufo 的模型控制草稿长度（#173） | [Gufo 适配](../src-tauri/src/gufo.rs) 根据已探测的能力生成有效参数。界面保留旧草稿值并展示引擎行为。 | Gufo 参数页与引擎测试；真实 Windows Gufo 启动验收 |
| 改桌面与 Rust 之间的参数或返回值 | [类型化 IPC](../src/lib/instanceIpc.ts) 和对应 Rust 命令。管理接口继续使用版本化的本机协议并脱敏返回值。 | Rust 和 TypeScript 共用的[手动预览样例](../scripts/fixtures/manual-command-preview.json) |

实际启动会直接核验引擎身份，并在准备完检查点后验证最终参数。预览不创建推理进程。管理端的校验可以读取草稿配置或已保存实例，使用默认引擎的只读预览不会写入绑定。桌面的保存队列与配置版本检查在命令执行前完成。

## 哪一层可以更新什么

| 状态 | 所有者与恢复方式 |
|---|---|
| 已保存配置 | Rust 配置层在写锁内比较启动前的设置，成功落盘后才公布规范化结果。若启动期间有人修改设置，保留新配置用于下次启动。冷恢复沿用原进程的启动快照，界面持有的草稿和下一次启动配置分别保留。 |
| 运行进程与路由监听 | 管理该进程的运行时负责启停。GUI 检查点冷恢复沿用本地进程所有权。桌面记录 PID、进程启动时间和可执行文件路径。 |
| 桌面显示与日志连接 | [快照对齐](../src-tauri/src/runtime_service/reconcile.rs) 根据已知所有者判定新增、替换和消失的进程。状态请求在本次桌面会话内排序。成功启停后，较早请求的迟到结果会被忽略。 |
| 错过停止事件的页面 | 后续快照仍携带已停止的后台实例 ID。相同 ID 已由前台接管时，旧后台记录失去更新权。实例配置删除后清理相应记录。 |
| 服务健康 | 后台快照中的运行记录表示进程存在。就绪来自健康探测；新进程尚无探测结果时显示等待。重复心跳可以补发状态，日志连接只为当前进程建立一次。 |

## 验证方式

使用 `npm run test:rust` 测试启动规则和快照变化，使用 `npm run test:browser` 测试页面行为。构建调试二进制后，`npm run test:management` 通过真实 CLI、stdio MCP 和测试引擎比对预览与实际参数；`npm run test:runtime-service` 覆盖后台交接拒绝、重放、路由及运行时退出。给后者设置 `LSM_TEST_PREVIOUS_RUNTIME_EXE`（前一版管理器可执行文件的绝对路径），可在独立数据目录验证旧运行时向新运行时交接。
